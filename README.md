# Tomas Club

Telegram-бот подписочного клуба и отдельная админка. Go + PostgreSQL, React + TypeScript + Vite + MUI, REST API, Docker Compose.

Реализована первая рабочая версия: редактирование сообщений, цепочки рассылок, пользователи и фильтры, подписочные сценарии, сохранение webhook, повторная проверка Lava, заявки в канал, отмена и истечение доступа. Интеграционные тесты используют настоящую PostgreSQL и локальные HTTP-серверы провайдеров. Реальные платежи и Telegram-канал еще необходимо проверить с вашими реквизитами. Ограничения перечислены ниже.

## Быстрый запуск

1. Скопировать `.env.example` в `.env` (если файла еще нет).
2. Задать случайный URL-safe `POSTGRES_PASSWORD` и пароль администратора. Получить bcrypt-хеш:

   ```sh
   cd backend
   ADMIN_PASSWORD='your-long-unique-password' go run ./cmd/setup hash-password
   ```

   Сохранить результат в `ADMIN_PASSWORD_HASH` в `.env` в **одинарных кавычках**, чтобы Compose не интерполировал `$`. Пустой хеш отключает вход. Хеш можно также получить после сборки через `docker compose run --rm --no-deps -e ADMIN_PASSWORD --entrypoint /app/setup backend hash-password`, предварительно задав `ADMIN_PASSWORD` в окружении терминала.
3. Из корня проекта:

   ```sh
   docker compose up -d --build
   docker compose ps
   ```

4. Открыть `http://localhost:8080` либо порт из `PORT`. `BASE_URL` должен точно совпадать с origin браузера, включая порт; это часть защиты от CSRF.

Для локального окружения, созданного при разработке, используется `http://localhost:8097`; локальный пароль находится в `.env`, поле `ADMIN_PASSWORD`. Этот файл игнорируется Git. Значение `ADMIN_PASSWORD` не требуется приложению: перед production удалить его и оставить только bcrypt-хеш.

Пустые Telegram/Lava credentials допускают проверку админки. Они не включают имитацию платежей и не дают пользователям оплаченный доступ.

## Сервисы

- `postgres` — постоянные данные в named volume, порт БД наружу не публикуется.
- `migrate` — одноразовый процесс SQL-миграций перед запуском приложений.
- `backend` — REST API и прием webhook.
- `worker` — тот же Go-бинарник с `WORKER_ENABLED=true`; обработка событий и scheduled jobs.
- `admin-frontend` — Nginx со сборкой React; проксирует `/api/`, `/webhooks/`, `/healthz` на backend.

Публичный listener по умолчанию привязан к `127.0.0.1`. Для production настройте внешний reverse proxy с HTTPS на этот порт, задайте HTTPS `BASE_URL`. Не выставляйте PostgreSQL в интернет. Сделайте резервное копирование volume и проверьте восстановление до запуска продаж. Compose предназначен для одного хоста, не обеспечивает его отказоустойчивость.

## Telegram

1. Создать бота через BotFather и приватный канал.
2. Добавить бота администратором с `can_invite_users` и `can_restrict_members`.
3. Задать `TELEGRAM_BOT_TOKEN`, отрицательный `TELEGRAM_CHANNEL_ID`, случайный `TELEGRAM_WEBHOOK_SECRET` длиной от 32 символов (`A-Z`, `a-z`, `0-9`, `_`, `-`).
4. Указать HTTPS `BASE_URL` и пересоздать сервисы: `docker compose up -d`. Ссылки поддержки задаются в inline-кнопках сообщений через админ-панель.
5. Выполнить:

   ```sh
   docker compose exec backend /app/setup
   ```

Команда проверяет права, создает invite link с заявками, регистрирует `/start`, `/buy`, `/status`, `/help` и webhook. Поддерживаются `message`, `callback_query`, `chat_join_request`. Секрет проверяется в `X-Telegram-Bot-Api-Secret-Token`. В канал принимается только тот Telegram ID, которому принадлежит действующая подписка. Бот обслуживает команды в личном чате.

Описания Menu Commands хранятся в сообщениях `command_*`. После их изменения повторно выполните `/app/setup`. При смене канала старый `runtime_settings.invite_url` нужно заменить после проверки нового канала. Участников, уже находившихся в канале до установки бота, нужно отдельно сверить: Telegram Bot API не предоставляет полную выгрузку списка участников.

## Lava.top

1. Создать один подписочный оффер с ценами для `MONTHLY`, `PERIOD_90_DAYS`, `PERIOD_180_DAYS` и `PERIOD_YEAR`.
2. Задать `LAVA_API_KEY`, `LAVA_OFFER_ID`, `LAVA_FOREIGN_CURRENCY`.
3. В интеграции Lava настроить HTTPS webhook `BASE_URL/webhooks/lava` с API-key authentication. Значение ключа — отдельный `LAVA_WEBHOOK_SECRET` длиной от 32 символов.
4. Включить события первой оплаты, ошибки оплаты, успешного/неуспешного recurring payment и отмены. Перечень и подтвержденные HTTP-контракты — в [разборе Lava](docs/lava-integration.md).
5. Проверить реальные покупки/продления/отмену на вашем оффере. При `unknown`/`creating` checkout сначала установить фактическое состояние в Lava; не создавать повторный контракт вслепую.

Пользователь выбирает в боте 1, 3, 6 или 12 месяцев. Backend передает соответствующий `periodicity` в Lava и сохраняет его в попытке оплаты и подписке. Точная сумма определяется оффером и показана на checkout. Активная подписка блокирует создание второго рекуррентного договора; продление выполняет Lava очередным списанием.

## Переменные окружения

| ENV | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL для Compose, URL-safe символы |
| `DATABASE_URL` | DSN для Go; Compose собирает его автоматически |
| `BASE_URL`, `PORT` | Публичный origin и локальный порт frontend |
| `ADMIN_PASSWORD_HASH` | bcrypt-хеш пароля администратора |
| `TELEGRAM_BOT_TOKEN` | Токен бота |
| `TELEGRAM_CHANNEL_ID` | Отрицательный числовой ID приватного канала |
| `TELEGRAM_WEBHOOK_SECRET` | Отдельный секрет Telegram webhook |
| `LAVA_API_KEY` | Ключ исходящих запросов Lava |
| `LAVA_WEBHOOK_SECRET` | Ключ входящих webhook Lava |
| `LAVA_OFFER_ID` | ID цены подписочного оффера |
| `LAVA_FOREIGN_CURRENCY` | `USD` или `EUR` |
| `PLAN_NAME`, `PLAN_PRICE_LABEL`, `PLAN_PERIOD_LABEL` | Текстовые данные тарифа |
| `DISPLAY_TIMEZONE` | IANA timezone для Telegram; БД — UTC, UI — timezone браузера |
| `WORKER_ENABLED` | Запуск worker; Compose задает для сервисов явно |
| `LISTEN_ADDR` | HTTP listener Go, по умолчанию `:8080` |

Секреты не передаются в Vite bundle и не должны попадать в Git. Перед первой оплатой бот запрашивает настоящий email для чека и уведомлений Lava; адрес сохраняется и повторно используется для продлений и отмены. В журнал не записываются запросы с токенами и email покупателя. Raw webhook в БД содержит персональные данные: ограничьте доступ и определите срок хранения.

## Архитектура и API

Подробности проектных решений — [docs/architecture.md](docs/architecture.md). Реализация: `backend/internal/app` содержит use cases, HTTP handlers и SQL; внешние клиенты — отдельные пакеты `lava` и `telegram`, конфигурация — `config`. Зависимости передаются конструкторами. Выделение repository-слоя из `app` оставлено для следующего этапа, чтобы не добавлять пустые обертки над SQL.

Финансовые изменения защищены транзакциями, блокировкой пользователя и уникальным ID платежа. Статус пользователя вычисляет SQL view `user_status`; он не устаревает между тиками worker. Кнопка «Оплатил» выполняет server-side проверку. Отмена сохраняет доступ до конца оплаченного периода. Перед новым удалением участника worker отдельно сверяет все его известные контракты с Lava: задержка webhook не должна приводить к исключению оплатившего пользователя. При ошибке проверки удаление откладывается; восстановление уже начатого unban не зависит от доступности Lava. Внешние запросы имеют таймауты, worker обрабатывает retry/backoff и Telegram `retry_after`.

`bot_messages.buttons` — JSONB с валидацией разрешенных действий вместо отдельной таблицы кнопок. System key неизменяем. Оплаченный срок хранится в подписке, платежи — отдельно; отдельная таблица периодов пока не используется. Telegram отправка и commit PostgreSQL не атомарны: после аварии уведомление может повториться, но платеж не зачисляется повторно.

Admin API использует cookie-сессии с HttpOnly, SameSite=Strict, Secure при HTTPS; изменяющие запросы требуют правильного Origin. Вход ограничен 20 попытками за 5 минут. Сессия действует 12 часов.

```text
POST   /api/login                 {"password":"..."}
POST   /api/logout
GET    /api/session
GET    /api/messages
GET    /api/messages/:id
PUT    /api/messages/:id           Message + version; конфликт версии = 409
GET    /api/messages/:id/media     Загруженное видео для предпросмотра
POST   /api/messages/:id/media     multipart: media_type + MP4 до 50 МБ
DELETE /api/messages/:id/media
GET    /api/broadcasts
POST   /api/broadcasts
PUT    /api/broadcasts/:id
DELETE /api/broadcasts/:id
GET    /api/mailings
POST   /api/mailings
PUT    /api/mailings/:id
DELETE /api/mailings/:id
GET    /api/mailings/:id/steps
POST   /api/mailings/:id/steps
POST   /api/mailings/:id/send
GET    /api/mailings/:id/runs
GET    /api/users                  ?status=active&auto_renew=true&search=...&page=1
GET    /api/users/:id              envelope items/total/page
GET    /healthz
```

`/users` возвращает `{items,total,page}` по 50 строк; Telegram ID — строка для безопасного отображения в JS. `/messages` и `/broadcasts` возвращают массивы. Изменения контента фиксируются в `audit_log`.

К сообщению можно прикрепить обычное MP4-видео или Telegram-кружок и выбрать его расположение до или после текста. Кружок должен быть квадратным MP4 продолжительностью не более минуты. При первой отправке файл загружается в Telegram, полученный `file_id` сохраняется и переиспользуется в следующих сообщениях.

Авторассылка выключена по умолчанию (нет шагов). Позиция задает порядок, при совпадении используется ID. Задержка — перед каждым шагом, сейчас минимум 1 секунда для тестирования. **Перед рабочим запуском рассылок вернуть минимум 60 секунд** в интерфейсе, проверке API и ограничении БД (новой миграцией после `021_broadcast_second_delays.sql`). После последнего шага цикл повторяется. При активной подписке пользователь исключается из цикла; после истечения возвращается к первому шагу. Отключенный или удаленный текущий шаг приводит к началу с первого включенного с его задержкой.

Разовая рассылка создаётся черновиком в отдельном разделе. Администратор добавляет сообщения и задержки, затем подтверждает отправку сейчас или выбирает в календаре будущие даты с отдельным временем по Москве для каждой. Календарь можно открыть повторно: добавить даты, изменить время или убрать ожидающие запуски. Даже если даты уже назначены, отдельная кнопка «Отправить сейчас» запускает дополнительную отправку и сохраняет расписание. Уже начавшиеся и завершённые запуски не меняются. В каждый назначенный момент worker отдельно фиксирует получателей, соответствующих выбранному статусу и уже запустивших бота, и проходит цепочку один раз без зацикливания. Каждый запуск хранит свой список получателей, время и результат. Пока хотя бы один запуск назначен или отправляется, редактор сообщений закрыт; название рассылки можно изменить в любое время. После завершения всех запусков можно изменить цепочку и аудиторию, затем отправить её ещё раз (с подтверждением) или назначить новые даты. Предыдущие результаты сохраняются в истории.

## Разработка и тесты

Нужны Go 1.26+, Node 22.12+ и Docker. Для локального backend передайте `DATABASE_URL`, `BASE_URL` и `ADMIN_PASSWORD_HASH`; для Vite dev используйте `BASE_URL=http://localhost:5173`. Dev proxy направляет `/api` на Go `localhost:8080`.

```sh
cd frontend
npm ci
npm run dev
```

Проверка:

```sh
make test
```

Интеграционные тесты создают изолированные схемы в БД, имя которой **обязательно заканчивается на `_test`**:

```sh
docker compose -f compose.test.yaml up -d --wait
cd backend
TEST_DATABASE_URL='postgres://test:test-local-only@localhost:55438/club_test?sslmode=disable' \
  go test -race -tags=integration ./...
```

Проверяются дубли и перестановка платежей, отмена, истечение/восстановление unban, конкурентный checkout, неоднозначная ошибка создания invoice, остановка рассылки, webhook auth, admin auth/CSRF и конфликт редактирования.

## Оставшиеся ограничения перед production

- Реальные Lava subscriptions и Telegram permissions/webhook еще не проверены с вашими ключами.
- Возвраты/chargeback сохраняются для операторского разбора; автоматическая политика не реализована.
- Неоднозначное создание invoice требует ручного восстановления; специального интерфейса для него пока нет. Если ответ Lava уже получен, его сохранение выполняется с отдельным ограниченным таймаутом, даже при отмене контекста обработки.
- Worker использует одного лидера на PostgreSQL advisory lock. Нагрузочные испытания, алерты и регламент разбора очередей еще нужны; задержки увеличатся при большом потоке.
- Preview отображает Telegram HTML, примеры значений переменных, кнопки, видео и кружки. Итоговый вид зависит от версии и темы приложения Telegram.
- Сейчас фиксированы технические интервалы worker: цикл событий 1 секунда, scheduled jobs около 30 секунд, reconciliation от 5 минут. Время авторассылки задается в БД.
