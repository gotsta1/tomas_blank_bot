# Lava.top: результат проверки API

Проверено 21 сентября 2026 года по [официальному порталу](https://developers.lava.top/en) и [Swagger](https://gate.lava.top/docs). Исходная спецификация сохранена в `lava-openapi.yaml`. Ниже отделены подтвержденные контракты от ограничений, которые требуют проверки с конкретным оффером.

| Вопрос | Подтверждение и реализация |
| --- | --- |
| Первый платеж | `POST /api/v3/invoice`, `email`, `offerId`, `currency`, `periodicity`. В коде запрещен `ONE_TIME`. |
| Период | `MONTHLY`, `PERIOD_90_DAYS`, `PERIOD_180_DAYS`, `PERIOD_YEAR`. Месячную подписку не представляем как фиксированные 30 дней. |
| Ответ создания | `id` — ID контракта; `paymentUrl` — ссылка оплаты. Локальная checkout attempt связывает его с Telegram ID. |
| Рекуррентный платеж | `contractId` — ID очередного контракта; `parentContractId` связывает его с первой покупкой. Не использовать parent ID как уникальный ID каждого списания. |
| Проверка | `GET /api/v1/subscriptions/{id}` по родительскому контракту; `GET /api/v2/invoices/{id}` для разрешения связи с родительским контрактом. |
| Отмена | `DELETE /api/v1/subscriptions?contractId=...&email=...`, успех — 204. Отмена не сокращает оплаченный период. |
| Даты | Subscription response содержит `datetime`, `expiredAt`, `cancelledAt`, `terminatedAt`; recurring payments содержат `datetime`. Отдельного достоверного поля следующей попытки списания в проверенной модели нет. |
| Подтверждение платежей | `status=COMPLETED` у первой покупки или элемента `recurrentPayments`; срок — `expiredAt`. Для завершенной активной подписки с нулевой тестовой суммой отсутствие даты компенсируется выбранным периодом от `datetime`; для платных договоров дата обязательна. |
| Email | Поле описано в запросе создания и обязательно при отмене. Бот запрашивает настоящий адрес перед первой оплатой, сохраняет его в собственной БД и передает в Lava для чеков и уведомлений. |
| Metadata | Произвольного `metadata`/`customData` в CreateInvoiceV3Request нет. Есть рекламные `clientUtm`; их не подменяем персональными идентификаторами. Сопоставление ведется в собственной БД. |
| Защита webhook | `X-Api-Key` либо Basic Auth согласно настройке интеграции. Реализован `X-Api-Key` с отдельным `LAVA_WEBHOOK_SECRET`; HMAC-подпись не выдумывается. |
| Дедупликация | Payment/subscription webhook не имеют универсального event ID: raw event получает хеш, финансовая дедупликация отдельно обеспечена уникальным ID платежного контракта и повторной сверкой с API. |

## Методы оплаты

- RUB: subscription-пример явно показывает `SMART_GLOCAL`; обе российские кнопки используют этот flow. СБП не принуждается: его наличие и рекуррентность должны быть проверены на checkout конкретного оффера.
- PayPal: `paymentProvider=PAYPAL`, USD или EUR.
- Зарубежная карта: валюта USD/EUR, провайдер не передается — используется выбор Lava по умолчанию.
- Apple Pay: отдельного enum нет; открывается зарубежный checkout, наличие Apple Pay определяется страницей провайдера.
- В Swagger есть противоречие: примеры содержат `UNLIMIT`, enum содержит `UNLIMINT`. Поэтому код не отправляет ни одно из этих спорных значений явно.
- `PAY2ME` и метод `SBP` описаны в API, однако пример подписки с этим сочетанием не найден. Не выдаем доступность разового способа за поддержку автопродления.

Подписи и пояснения платежных кнопок находятся в БД и редактируются. Значения API определены адаптером; админский контент не может подменить финансовую логику.

Перед выбором региона и способа оплаты бот предлагает четыре периода: 1, 3, 6 и 12 месяцев. Один `LAVA_OFFER_ID` используется со значениями `MONTHLY`, `PERIOD_90_DAYS`, `PERIOD_180_DAYS` и `PERIOD_YEAR`. При действующей подписке второй договор не создается: дальнейший доступ продлевается рекуррентным списанием Lava.

## События и их обработка

Основные подписочные события: `payment.success`, `payment.failed`, `subscription.recurring.payment.success`, `subscription.recurring.payment.failed`, `subscription.cancelled`.

Обработчик сохраняет аутентифицированное событие до ответа 200. Worker получает актуальную подписку, записывает завершенные списания и обновляет доступ транзакционно. Повторные или переставленные события не добавляют дни. Отмена и прекращение доступа сохраняются при последующих устаревших ответах. Ошибка рекуррентной попытки сама по себе не сокращает период.

`refund.success` и `chargeback.initiated` имеют отдельный envelope (`event_id`, `event_type`, `data`). Они сохраняются и остаются в очереди с явной ошибкой для разбора оператором. Автоматическая политика полного/частичного возврата и спора не входит в текущую реализацию: не включать эти события без согласованного регламента. Неизвестные обычные события сохраняются и пропускаются с записью в журнале.

## Ограничение создания invoice

В изученном контракте создания не найден документированный idempotency key. До внешнего вызова записывается checkout attempt с уникальным ограничением на незавершенную покупку пользователя. После таймаута повторное создание блокируется состоянием `unknown` (после аварийного завершения процесса может остаться `creating`). Это предотвращает случайную вторую рекуррентную подписку, но требует операторского восстановления по кабинету Lava. Нельзя просто снять блокировку и повторить оплату, пока не установлено, был ли создан первый контракт.

Если пользователь повторяет оплату с уже созданной ссылкой, бот возвращает прежнюю ссылку. После 15 минут он дополнительно проверяет invoice в Lava. При `NEW` или `IN_PROGRESS` прежняя ссылка остаётся единственной; при `COMPLETED` бот предлагает проверить оплату; только подтверждённый `FAILED` позволяет создать новый invoice. Недоступность API Lava не освобождает старую заявку. Локальный возраст заявки сам по себе не считается сроком действия ссылки: API не предоставляет подтверждённого времени её истечения.

## Что необходимо подтвердить перед настоящими продажами

Создание и первая оплата конкретного оффера, реальные webhook, повторное списание, отмена, сохранение доступа после отмены, `expiredAt` на каждом переходе, доступные методы оплаты для выбранных стран и валют. Эти проверки требуют настроенной интеграции Lava и тестового покупателя; чтение Swagger и HTTP-тесты их не заменяют.

При полученном ответе создания invoice запись результата в БД использует отдельный таймаут 10 секунд и не отменяется вместе с контекстом вызвавшей задачи. Это закрывает случай отмены между ответом Lava и сохранением; аварийное завершение процесса или недоступность БД по-прежнему требуют восстановления оператором.
