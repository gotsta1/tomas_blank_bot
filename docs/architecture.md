# Стек и архитектура

Статус: стек зафиксирован, первая реализация добавлена. Ниже сохранен первоначальный проект архитектуры; фактическая структура, упрощения и ограничения описаны в [README](../README.md). Результат завершенной сверки Swagger — в [lava-integration.md](lava-integration.md).

## Фактический масштаб первой версии

Реализация представляет собой приложение для одного подписочного клуба с ориентиром около 2 500 пользователей приватного Telegram-канала. Оно развёртывается на одном сервере через Docker Compose: отдельные процессы API и worker, PostgreSQL, админка и HTTPS reverse proxy. Задачи хранятся в PostgreSQL; одновременно работает один лидер worker. Это сознательно простая архитектура MVP, а не подтверждённая нагрузочным тестом ёмкость в 2 500 одновременных запросов.

## Стек

- Backend: Go, HTTP REST API, Telegram Bot API и Lava.top API.
- Frontend: React + TypeScript, Vite, MUI.
- База данных: PostgreSQL; схема управляется SQL-миграциями.
- Запуск: Docker Compose для backend, worker, admin-frontend, postgres и одноразового сервиса migrate.
- В production публичный HTTPS завершается на reverse proxy. Frontend и API доступны на одном origin.

MUI выбран для таблиц пользователей, фильтров и форм редактора. Админка содержит только `/messages`, `/broadcasts`, `/users` и экран входа.

## Предлагаемая структура

```text
backend/
  cmd/server/             # REST API и прием webhook
  cmd/worker/             # события, доставка, рассылки, истечение доступа
  internal/config/
  internal/domain/
  internal/service/
  internal/repository/    # PostgreSQL и транзакции
  internal/http/          # маршруты, авторизация, валидация
  internal/telegram/     # клиент Telegram Bot API
  internal/lava/         # клиент и DTO провайдера
  internal/jobs/
  migrations/
frontend/
  src/api/
  src/components/
  src/pages/messages/
  src/pages/broadcasts/
  src/pages/users/
deploy/
docs/
compose.yaml
.env.example
README.md
```

Server и worker используют общую бизнес-логику. Очередь задач находится в PostgreSQL; отдельный брокер на этом этапе не требуется.

## Предлагаемая схема БД

| Таблица | Назначение и ограничения |
| --- | --- |
| users | Уникальный telegram_user_id BIGINT, имя, username, email, первый запуск и последняя активность |
| subscriptions | Пользователь, offer, идентификаторы провайдера, статус, auto_renew, started_at, expires_at, next_payment_at, cancelled_at |
| subscription_periods | Подтвержденные оплаченные периоды и связь с платежом; основание предоставления доступа |
| payments | Invoice/contract/payment identifiers в отдельных полях, сумма NUMERIC, валюта, тип, статус и время платежа |
| checkout_attempts | Состояние создания invoice; защита от параллельных нажатий и повторной покупки при неопределенном ответе API |
| webhook_events | Провайдер, внешний идентификатор при наличии, ключ дедупликации, JSONB payload, статус обработки, ошибка и число попыток |
| bot_messages | Уникальный неизменяемый key, название, шаблон текста, parse_mode и enabled |
| bot_message_buttons | Сообщение, подпись, разрешенное системное действие или URL, строка, порядок, enabled |
| broadcast_steps | Сообщение, порядок, положительная задержка, enabled |
| broadcast_user_state | Уникальный пользователь, текущий шаг, время последней и следующей отправки |
| outbox_jobs | Надежная доставка команд, повторные попытки, блокировка задач несколькими worker |
| channel_access | Желаемое и подтвержденное состояние доступа, стадия ban/unban, последняя ошибка |
| admin_sessions | Хеши токенов сессий, срок действия и отзыв |
| audit_log | Изменения контента, подписок и административные операции |

Все времена — TIMESTAMPTZ; соединения работают в UTC. Деньги не хранятся во float. Внешние идентификаторы платежей уникальны в рамках провайдера после проверки их семантики в API. Нельзя считать contractId идентификатором отдельного списания без такой проверки.

Статус пользователя вычисляется из оплаченных периодов: active при действующем доступе, expired при наличии завершенного периода, иначе new. Если статус материализуется для поиска, он обновляется в одной транзакции с периодами. Решение о доступе всегда повторно проверяет expires_at.

## Критические правила

1. Сначала проверить подлинность webhook и надежно сохранить событие, затем отвечать 2xx. Финансовую обработку выполнять транзакционно; уведомления создавать через outbox.
2. Telegram update дедуплицировать по update_id. Для Lava использовать документированные идентификаторы события и платежа; хеш payload сам по себе не гарантирует финансовую идемпотентность.
3. Отмена автопродления не аннулирует оплаченный период. Поздний webhook не должен откатывать более свежий подтвержденный статус.
4. Перед созданием оплаты проверять действующую подписку и незавершенные checkout attempts. Не повторять создание invoice автоматически после неоднозначного сетевого сбоя без reconciliation.
5. Перед approve, исключением из канала и рассылкой повторно проверять доступ. Сериализовать операции одного пользователя; после внешнего вызова повторно сверять желаемое состояние, поскольку транзакция БД не охватывает Telegram API.
6. Ban и последующий unban хранить как отдельные повторяемые стадии, чтобы сбой не оставил пользователя навсегда заблокированным.
7. Все тексты и подписи кнопок находятся в БД. Системные действия и разрешенные переменные шаблонов проверяет backend; редактирование контента не позволяет изменить финансовую логику.
8. Авторизация админки: серверные сессии, HttpOnly/Secure/SameSite cookie, защита изменяющих запросов от CSRF, ограничение попыток входа. Секреты не попадают в Vite bundle.
9. Workers используют ограниченную конкурентность, context, таймауты, retry с backoff и обработку Telegram retry_after. Завершение процесса — graceful shutdown.

## Первичная сверка документации

Проверено 2026-09-21:

- [Lava.top](https://developers.lava.top/en): описаны payment.success, payment.failed, subscription.recurring.payment.success, subscription.recurring.payment.failed, subscription.cancelled, refund.success и chargeback.initiated.
- Lava webhook поддерживает Basic Auth либо X-Api-Key. Не следует придумывать HMAC-подпись. Форматы payment/subscription и refund/chargeback различаются.
- [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook): webhook поддерживает secret_token, передаваемый в X-Telegram-Bot-Api-Secret-Token. Updates необходимо обрабатывать идемпотентно из-за повторной доставки.
- [Lava Swagger](https://gate.lava.top/docs) — источник точных контрактов API. Наличие POST /api/v3/invoice в общей документации еще не подтверждает все параметры subscription flow.

До реализации Lava-клиента требуется завершить сверку Swagger: создание рекуррентной подписки, отмена, server-side проверка, идентификаторы отдельных списаний, поля дат оплаченного периода, обязательность email, metadata, поддерживаемые провайдеры и применимость методов оплаты к подпискам. СБП, Apple Pay и другие названия кнопок нельзя автоматически переносить в API enums.

## Проверка реализации

Обязательны интеграционные проверки PostgreSQL для повторных и переставленных webhook, конкурентных checkout, отмены с сохранением доступа и гонки продления с удалением. Отдельно проверяются навигация бота, восстановление ban/unban, остановка рассылки после оплаты и авторизация REST API. Проверка настоящих подписок, webhook и прав бота проводится в настроенном окружении; один успешный запуск контейнеров не означает готовность платежной интеграции к production.
